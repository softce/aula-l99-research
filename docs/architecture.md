# Архитектура: что делает каждый узел

[К оглавлению](../README.md)

## Два USB-устройства и связь между контроллерами

| Узел | Наблюдаемый ID | Роль в нашей реализации |
|---|---|---|
| Основная клавиатура | `0C45:800A` | Обычный ввод, преобразование команд сенсорной панели в клавиши |
| Экран | `EEEF:268A` | USB Serial, интерфейс и runtime-переменные |

COM-номер назначается Windows: нельзя фиксировать чужой `COM7`. Изученная программа ищет ровно один порт с VID/PID экрана. Схема ниже описывает поведение и анализ обработчиков; физический UART между платами отдельно логическим анализатором не захватывался.

У картинки кнопки есть изображение, координаты, код возврата и переход. Изменив изображение лампы, мы не создаём новую аппаратную команду. Штатный экранный MCU обрабатывает касание, затем клавиатурный MCU преобразует известный код в событие ввода. И только приложение на ПК придаёт ему смысл «включить свет».

## Один полный цикл нажатия

1. На странице HOME нажимаем плитку.
2. Touch-запись содержит известный экрану код, например `0x003B`.
3. Штатная логика передаёт код основной клавиатуре.
4. Её таблица превращает этот код в USB HID usage `0x59` — NumPad 1.
5. Windows hook узнаёт scan code `0x4F` и вариант virtual key для текущего Num Lock.
6. Hook подавляет нажатие/отпускание и передаёт событие рабочему потоку. HTTP не выполняется внутри callback клавиатуры.
7. Рабочий поток проверяет назначение и состояние HA, затем вызывает разрешённый сервис.
8. UI приложения показывает состояние, полученное от HA. Удержание кнопки не должно повторять команду.

Путь 2–4 подтверждён статическим разбором и частичной эмуляцией клавиатурного обработчика; путь от касания до управления HA подтверждён пользовательской проверкой на устройстве. Это разные виды доказательств.

## Почему кнопок 12, хотя цифр 10

Используются 1–9, 0, decimal и минус. Для 12 плиток не нужен новый HID-протокол.

| Слот панели | Экранный код | HID usage | Windows scan code | VK с Num Lock / без него |
|---:|---|---|---|---|
| 1 | `003B` | `59` | `4F` | `61 / 23` |
| 2 | `003C` | `5A` | `50` | `62 / 28` |
| 3 | `003D` | `5B` | `51` | `63 / 22` |
| 4 | `0038` | `5C` | `4B` | `64 / 25` |
| 5 | `0039` | `5D` | `4C` | `65 / 0C` |
| 6 | `003A` | `5E` | `4D` | `66 / 27` |
| 7 | `0034` | `5F` | `47` | `67 / 24` |
| 8 | `0035` | `60` | `48` | `68 / 26` |
| 9 | `0036` | `61` | `49` | `69 / 21` |
| 10 | `003F` | `62` | `52` | `60 / 2D` |
| 11 | `0040` | `63` | `53` | `6E / 2E` |
| 12 | `0033` | `56` | `4A` | `6D / 6D` |

Все числа в таблице — hex. Экранный код, HID usage, scan code и VK **не взаимозаменяемы**. Отдельные E0 navigation keys и синтетический ввод пропускаются. Сочетания с Shift/Ctrl/Alt/Win не должны запускать действия. Верхний ряд цифр имеет другие scan codes.

При этом `WH_KEYBOARD_LL` не сообщает, от какого физического устройства пришла клавиша. Значит, мы занимаем соответствующие клавиши всех нампадов. Переход к per-device обработке требует отдельного решения: Raw Input различает устройства, но сам по себе не обеспечивает такое же глобальное подавление ввода. Это не исправляется одной галочкой.

## Home Assistant и семантика действий

Пример вымышленного назначения: слот 1 → `switch.example_light` → переключение. `button.example_play` вызывает `button.press`. Это примеры структуры, не существующие объекты какой-либо установки.

В реализованном мосте:

- `toggle` читает актуальное состояние и выбирает `switch.turn_on` или `switch.turn_off`;
- `on`/`off` задают состояние;
- `press` вызывает `button.press`;
- `pulse` вызывает только `switch.turn_on`: **короткий импульс обязан обеспечивать сам HA или устройство**. Приложение не добавляет таймер выключения.

При неизвестном состоянии действие не должно выполняться. Неудачный HTTP-запрос нельзя автоматически повторять для ворот: сервер мог уже принять команду, даже если ответ потерян. Старые события отключённой сессии не должны исполняться после переподключения. Состояние реле не равно положению ворот.

## Обратный путь: значения датчиков

Опрос семи объектов HA формирует шесть чисел и строку статуса. Интервал рабочего цикла — время запросов плюс примерно 5 секунд ожидания, не гарантированные ровно 5 секунд.

| Поле | Источник и проверка |
|---|---|
| PV сейчас | Числовой state, единица `W` |
| Сеть сейчас | Числовой state, `W`; отрицательное значение допустимо |
| Заряд | State, `%`, диапазон 0–100 |
| Пол | `climate.example_floor`, `attributes.current_temperature`; предполагаются °C |
| PV за день | Сумма двух источников `kWh`; не складывать датчик с уже включённым в него компонентом |
| Сеть за день | State, `kWh` |

`unknown`, `unavailable`, неправильная единица, нечисловое значение дают `--`. Для температуры исходный форматтер не выполнял конверсию °F→°C: при переносе нужно явно согласовать единицы HA. Направление знака мощности сети зависит от интеграции и не определяется этим проектом.

Блок RAM и контрольная сигнатура описаны в [protocol.md](protocol.md). Частые обновления чисел пишут RAM, не ресурсную flash. Текстовые поля уже присутствуют в изменённом UI. Полноценной потоковой трансляции любого интерфейса ПК на экран здесь нет.

## Что нужно для фонового приложения

Наше Windows-приложение умеет трей, автозапуск и назначение сущностей. Токен хранится отдельно с Windows DPAPI, не в экспортируемом JSON. При переносе на другой ПК токен вводится заново; DPAPI-файл не является переносимым секретом. Автоматическое включение перехвата следует разрешать только после настройки и проверки панели.

Рабочая архитектура не требует ежедневной перепрошивки: новые назначения меняются на ПК. Но картинка и подписи на самой клавиатуре в этой реализации статичны и меняются отдельной сборкой UI. Цвет плитки экрана не подтверждает реальное состояние HA.
