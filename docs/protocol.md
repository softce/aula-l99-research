## Runtime-переменные экрана: реально использованный путь

Мост открывает USB Serial `EEEF:268A`: 115200, стандартные 8N1, DTR/RTS выключены. Запись начинается только после чтения сигнатуры подходящего UI. Наличие сигнатуры — проверка соглашения приложения с ресурсным образом, не криптографическая аттестация всей firmware.

Короткий runtime-кадр:

```text
5A A5 | length:u8 | body | CRC16(body):LE16
length = len(body) + 2
CRC16: reflected polynomial 0xA001, init 0xFFFF

read body:  03 | word_address:BE16 | word_count:BE16
write body: 10 | word_address:BE16 | word_0:BE16 | word_1:BE16 | ...
```

Read-ответ в используемом клиенте начинается с тела запроса, затем содержит значения слов BE16. Записи отправлялись чанками до восьми слов и проверялись чтением. Отсутствие write-ACK само по себе не считается успешной записью. Этот канал обновляет runtime RAM; его нельзя путать с ISP-загрузкой.

Адреса ниже — **16-битные индексы runtime-слов**, не offsets UI-файла и не CPU-указатели:

| Адрес | Содержание |
|---|---|
| `0x0600` | PV сейчас |
| `0x0608` | Мощность сети |
| `0x0610` | Заряд |
| `0x0618` | Температура пола |
| `0x0620` | PV за день |
| `0x0628` | Получено из сети за день |
| `0x0630` | Статус/время последнего обновления |
| `0x0638..0x0639` | Сигнатура: слова `0x454E, 0x4531` — `ENE1` |

Каждое текстовое поле занимает 8 слов = 16 байт. Строка ASCII не длиннее 15 байт, дополнена нулями до 16. Семь строк дают 56 слов. В памяти и передаче пары ASCII-байтов упаковываются как BE16. Пример синтетических данных можно получить командой `python tools/runtime_codec.py`; скрипт только печатает байты, ничего не отправляет.

При потере связи приложение пытается записать `--` и `OFFLINE`, если экран доступен. При остановке отправителя последние числа могут остаться на устройстве: штатный виджет сам по себе не знает, насколько они свежие. Строка времени полезна для обнаружения устаревших значений.

## Три разных семейства пакетов

1. Короткие `5A A5` runtime-кадры выше — переменные UI.
2. Расширенные runtime-кадры с `5A A5 00`, BE16 длиной и BE32 адресом — отдельный формат. Его примеры есть в `tools/protocol_reference.py`. Не все SDK-команды проверены на L99.
3. ISP-пакеты updater, например `4A 30`, — другой режим и другие адреса. Офлайн-кодек не является полной последовательностью erase/program/finish.

В разобранном ISP_V2.2 EXE с SHA256 `64ebb98d66af0fc03484e0528a9467bdce410d0d86305e6d757246d4889df476` функция VA `0x00403EA0` формирует:

```text
4A 30 | offset:LE32 | payload_length:LE16 | payload | CRC32:LE32
```

CRC32 — отражённый IEEE polynomial, init=0, xorout=0, по prefix+payload. Это не стандартный вызов `zlib.crc32(data)` без коррекции. `123456789` даёт `0x2DFD2D88`; CRC16/MODBUS той же строки — `0x4B37`.

В этой версии updater запрос `6D 01 selector` и сравнение flash ID с `0x00EFAA21` выбирают HFD V2.2/V2.3. В `Flash.ini` `EFAA21` соответствует W25N01GV. Это анализ программы и списка поддерживаемых чипов, не измерение flash нашего экземпляра. Нельзя выбирать V2.3 только потому, что номер больше.

## Почему LT7689 оказался ложным начальным ориентиром

В SDK LT7689 встречается тот же USB ID, но updater поддерживает несколько семейств. В извлечённых HFD `.bin` startup корректно дизассемблируется как little-endian M*Core:

```text
V2.2: base/VBR 0x6000A000, entry 0x60011620
V2.3: base/VBR 0x60010000, entry 0x600174B0
startup SP: 0x00874FFC
```

Первое слово — адрес входа, не ARM initial MSP. Инструкции `mtcr ... vbr`, startup и карта памяти согласуются с LT168. Для конкретных offsets всегда сверяйте хеш: одинаковые имена HFD_Code встречаются с разным содержимым.

Карта **семейства LT168** по документации производителя:

| Область | CPU address |
|---|---|
| Boot ROM, 8 KiB | `0x00000000..0x00001FFF` |
| SRAM, 768 KiB | `0x00800000..0x008BFFFF` |
| QSPI0 / QSPI1 / QSPI2 mapping | `0x60000000 / 0x70000000 / 0x80000000` |
| USB controller / watchdog | `0x40160000 / 0x40130000` |

Это не измеренный flash layout L99. Bootloader dump и независимое аппаратное восстановление нашего экземпляра не получены. Фоторазборка другой L99 сообщает HFD168BDP, HFD80CP100 и GT911; эквивалентность HFD168BDP конкретному LT168 pinout остаётся гипотезой. LT7689 SDK полезен для сопоставления UI-протокола, но не как готовая CPU/linker-база нашей платы.

## Основная клавиатура: важная поправка про resource 4000

Keyboard reset EXE содержит и ZIP с `SN32F290.hex`, и отдельный PE `RT_RCDATA` resource **4000**. Поиск только HEX пропускает существенный образ.

| Поле | Значение |
|---|---|
| Keyboard EXE SHA256 | `0a946a5d41a872f32e3f3cbdd0d73f9dd7058ea17d3f2a89b2b1bf5c3ed6b217` |
| Resource file offset / RVA | `0x1BAA4C / 0x1C764C` |
| Размер | 262144 байта |
| Resource SHA256 | `e5e43f6babdcc3e1e6390026e8ae5b66dffc40535105cb38be019a95a5bfde00` |
| Initial SP / reset vector | `0x20002F60 / 0x00007F95` |
| USB descriptor offset | `0x14160`: `0C45:800A`, bcdDevice `0106` |
| AULA L99 UTF-16 string | `0x14314` |

Штатный updater действительно загружает этот PE-ресурс. В его исполняемой таблице SN32F290 найден boot PID `0C45:7140`; это сильнее старого неактивного INI-шаблона, но всё ещё не live-идентификация bootloader экземпляра. Конкретный MCU и разводка матрицы для QMK не установлены. Родственный Ajazz-порт не является прошивкой L99.

## От экранного кода до HID; почему нельзя просто вписать F13

Адреса экранной стороны относятся к официальному HFD V2.3 SHA256 `a76806ada9648d2672bbebead8a9bb396c0bc6f3a0a071e22e99001ac3359d03`:

- `0x6002248C..0x600224B4`: формирование `41 FF FF key_hi key_lo`, вызов передатчика `0x60049D98`.
- В keyboard resource 4000 по `0x127EA..0x1281E` разбираются заголовок/ветка `41 FF FF`.
- Коды `0x30..0x40` выбирают счётчики в RAM `0x200022C4`; функция `0x688..0x6CA` формирует нажатие/отпускание.
- Таблица клавиш — **`0x19D7C`**, сериализатор — `0x2596`.

Для `0x003B/0x003C` выбираются HID usages `0x59/0x5A`, то есть NumPad1/2. Запись `0x0068/0x0069` в UI не превращает их в F13/F14: в этой ветке такой экранный код не создаёт нужного события.

В ограниченной эмуляции работал вариант с экранными кодами 1/2 и заменой двух байтов **клавиатурной** таблицы по `0x19D8D/0x19D8E` на HID usages `0x68/0x69`. Исполнялись реальные функции, получены буферы F13/F14, проверены ещё 254 младших кода. Но не моделировались полный boot/main loop, MMIO и реальная USB-передача; возможные динамические конфликты полностью не исключены. Этот вариант не загружался на клавиатуру.

Аудит штатного keyboard updater показал 4096 блоков по 64 байта — **256 KiB с адреса 0** даже ради двух изменённых байтов. Контрольная сумма — сумма LE16 по модулю 65536, не подпись и не полный readback. Поэтому рабочий проект остался на перехвате нампада: он позволил получить HA-панель без экспериментальной замены кода основной клавиатуры.
