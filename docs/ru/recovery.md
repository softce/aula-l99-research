# Заводское восстановление и уроки экспериментов

[К оглавлению](../../README.ru.md)

## Сначала различить три компонента

1. Firmware основной клавиатуры — отдельный keyboard reset EXE.
2. Исполняемый код MCU экрана — `HFD_Code_V2.2.bin` / `HFD_Code_V2.3.bin`.
3. Ресурсы/страницы экрана — `UartTFT-II_Flash.bin`.

Наличие полного reset-пакета не означает наличие полного backup конкретной платы. Пакет не доказывает, что загрузчик останется доступен при произвольной ошибке. Наши успешные UI-эксперименты сохраняли исполняемую логику; универсальное аппаратное recovery не проверено.

## Зафиксированный официальный пакет

## Что произошло на нашем экземпляре

В [инструкции AULA](https://aulastar.com/faq/818.html) описана последовательность Fn + X → 0 → 6. На нашем экземпляре эта попытка не дала ожидаемого результата. Пользователь сообщил, что с подключением USB **Fn+Пробел примерно 5 секунд** позволило начать обновление. Это наблюдение одной конфигурации, не универсальная замена официальной инструкции для всех ревизий.

После одного из ранних экранных опытов вводились неправильные символы. Запуск штатного `L99 keyboard reset firmware … .exe` восстановил ввод; отображалась версия 1.06. Изменённая оранжевая иконка экрана осталась. Значит, в этом случае восстановление клавиатурной части не отменило ресурсную правку экрана.

**Причина неправильных символов не установлена.** Reset меняет несколько условий; он не доказывает повреждение MCU именно из-за изменения картинки. Позже пользователь подтвердил, что новый нампад и клавиатура работают нормально.

В отдельных UI-комплектах использовался `HFD_ISP_TOOL_V1.31.exe` с ресурсным образом под штатным именем `UartTFT-II_Flash.bin`, без HFD_Code и keyboard MCU-файлов. Updater всё равно передаёт весь ресурсный образ; наличие только UI-файла не даёт гарантии восстановления после обрыва питания.

Перед ручным обновлением закрывались AULA Driver и наш мост, освобождался COM-порт, сохранялась известная рабочая база. Ожидалось штатное завершение updater, затем переподключение и проверка обычного ввода, экрана и панели. Это описание выполненной процедуры, не автоматический flasher из данного репозитория. На устройстве с другой ревизией сначала нужен свой проверенный план восстановления.

## Неудачные опыты, которые полезно не повторять

### Красивое превью не равно аппаратному результату

Ранняя версия «цифровые часы + энергия» дала полосы и испорченную графику на устройстве. Наблюдение подтверждено фотографией; единственная аппаратная причина не доказана. Поэтому не выдаём тот вариант как рабочий и не делаем вывод «любой LT encoder корректен», если он только проходит собственный decoder.

### Цвет числового поля — не обязательно RGB888

В исследованных полях потребовалась корректная интерпретация RGB565. Подстановка привычного RGB888 дала неправильный вид. В окончательных часах использованы проверенные значения: чёрный `0x0000`, белый `0xFFFF`.

### Кириллица штатным шрифтом выглядела плохо

Длинные русские надписи в неудачном формате получались разреженными. Для постоянных подписей выбраны картинки; меняющиеся числа остались ASCII. Это решение задачи дизайна, а не универсальный Unicode-патч.

### Значения могут остаться на экране после остановки передатчика

CPU/GPU 100% в прежних опытах не были достаточным доказательством настоящей загрузки компьютера. В дальнейшем проверялась вся цепочка: источник → передатчик → readback RAM → видимое значение. Для HA часы сначала показали значения после выхода/повторного открытия страницы, затем пользователь подтвердил регулярные обновления без переключения. Причина первого пустого отображения осталась неизвестной; ради неё прошивку повторно не меняли.

## Что ещё требуется для уверенного recovery

- Точная маркировка MCU и ревизия обеих плат.
- Проверенные сервисные контакты и способ входа при неработающем приложении MCU.
- Считанные и верифицированные области конкретного устройства, включая индивидуальные данные.
- Проверка пути восстановления на отдельном экземпляре, а не предположение по похожей Ajazz.

У документации семейства LT168 есть аппаратные boot/debug-сигналы, у SN32 — собственный BOOT. Переносить распиновку на HFD-маркировку без доказательств или замыкать площадки по чужой фотографии нельзя. Наличие этих направлений исследования не означает, что такой recovery уже сделан для L99.
